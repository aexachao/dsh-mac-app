# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Harness** wraps the web workbench of [DeepSeek Harness](https://github.com/deepseek-ai/dsh) (`dsh`) in a native macOS app: launching the app starts the `dsh web` service, quitting stops it. Pure SwiftUI + AppKit + WKWebView, no Electron. SwiftPM package `DSHWeb` (executable target), no external dependencies.

The service runs as a direct child process, `node <dsh>/lib/bin.js --profile web`. Release builds **bundle** a pinned Node.js and the whole dsh dependency tree inside the `.app` (`BUNDLE_RUNTIME=1`); when that is absent — every `swift build` / `swift run` dev build — the app falls back to the user's own Node plus the npx cache. See *Runtime resolution* below.

## Commands

```bash
swift build                                  # debug build
swift test                                   # all unit tests (swift-testing, not XCTest)
swift test --filter WebViewNavigationTests   # one suite
swift test --filter externalLinkOpensInBrowser  # one test

./scripts/build.sh                # universal (arm64 + x86_64) → dist/Harness.app → ~/Applications
ARCHS=arm64 ./scripts/build.sh    # single-arch, much faster for local iteration
NO_INSTALL=1 ./scripts/build.sh   # build only, skip install (CI uses this)

# release shape: pinned node + dsh vendored into the .app (single-arch only)
BUNDLE_RUNTIME=1 ARCHS=arm64 NO_INSTALL=1 ./scripts/build.sh
# + notarization (needs a Developer ID cert and App Store Connect credentials)
CODESIGN_IDENTITY="Developer ID Application: … (TEAMID)" NOTARIZE=1 \
  BUNDLE_RUNTIME=1 ARCHS=arm64 ./scripts/build.sh

PRECHECK_ONLY=1 ./scripts/notarize.sh dist/Harness.app   # local signature check, no upload
./scripts/make-dmg.sh dist/Harness.app /tmp/test.dmg     # dmg only (unsigned when CODESIGN_IDENTITY is empty)
./scripts/vendor-runtime.sh arm64 /tmp/rt                # vendor the runtime alone
./scripts/check-upstream.sh                              # update runtime-pins.json to upstream
```

`build.sh` env vars: `VERSION`, `BUILD` (default: derived from `git describe` + commit count), `ARCHS`, `NO_INSTALL`, `BUNDLE_RUNTIME`, `NOTARIZE`, `CODESIGN_IDENTITY` (default `Harness Local Signing`; falls back to ad-hoc). Prefer the stable self-signed identity — ad-hoc signatures change every build, which makes macOS re-prompt for TCC folder permissions each time.

**Gotcha:** the `.build*` directories cache absolute module-cache paths. If the repo is moved, `swift build`/`swift test` fails with `missing required module 'SwiftShims'`. Fix: `rm -rf .build .build-arm64 .build-x86_64`.

## Architecture

### Manual AppKit entry, deliberately
`main.swift` creates `NSApplication` + `AppDelegate` directly instead of using the SwiftUI `App` protocol. Reason: SwiftUI continuously rebuilds the default main menu and clobbers the custom bilingual menu bar. Consequences that must be preserved:

- `MenuBuilder.rebuild()` sets the menu twice (immediately + on the next main-queue tick) to cover both override timings.
- `MenuBuilder.startGuard()` runs a 1 s `Timer` that compares `NSApp.mainMenu` against `lastMenu` and rebuilds when SwiftUI has replaced it.
- Windows are created by hand (`NSWindow` + `NSHostingView`); the settings panel and log window are AppKit singletons (`SettingsPanel`, `LogPanel`) rather than SwiftUI `Settings`/`WindowGroup` scenes, so menu actions can open them repeatedly.
- `MenuBuilder.dumpMenuState` records the menu structure on every rebuild and every third guard tick. It is live debug instrumentation, not dead code. The write policy lives in `MenuStateLog`: the periodic tick is written **only when the structure changed** (`Event.dedupes`, true for `.tick` alone), the file is capped at 256 KB and wraps from the beginning, and it goes to `~/Library/Logs/Harness/menu-state.log` — not `/tmp`. Without dedupe the guard timer wrote the same unchanged structure every 3 s and reached 55 MB in a release build, burying the handful of lines that actually mattered. The name deliberately lacks `LogRotation.filePrefix`, so `LogFileSink`'s rotation neither counts it toward the 16 MB directory ceiling nor deletes it.

### Background residency: closing the window is not quitting (`MainWindow`)
The agent's work runs in the dsh service; the window is only its client. Stopping the service on window close cuts a running task in half — exactly what closing a browser tab does, and exactly what a native shell exists to avoid. So `applicationShouldTerminateAfterLastWindowClosed` returns **false**, and only `⌘Q` / menu quit / Dock-quit reach `applicationShouldTerminate` → `ServerManager.stop()`. Four pieces hold this up, and none of them fails at compile time:

- **`MainWindow.shared` holds the window strongly *and* sets `isReleasedWhenClosed = false`** (`MainWindow.configure`, split out so a test can pin it). Both are required: without the flag AppKit releases the window on close and the next `show()` touches freed memory; without the strong reference the window is reclaimed after the last close and only the content view could be rebuilt.
- **The `NSHostingView(rootView: ContentView())` is built exactly once.** Rebuilding it re-runs `ContentView.onAppear` (`server.start()`, `beginUserActivity()`), and the `WebViewController` lives in `AppState.shared` precisely so reopening the window shows the page as it was left — scroll position and half-typed input included.
- **`applicationShouldHandleReopen` ignores `hasVisibleWindows`.** `LogPanel` and `SettingsPanel` are windows too, so "main window closed, log panel open" reports `true`; obeying the parameter would strand the main window with no way back. Calling `show()` on an already-front window just brings it forward, which is the right answer to a Dock click anyway.
- **`ServerManager.start()` also guards `.external`.** An adopted server has no `process`, so the `process == nil` guard alone would let a second `start()` re-probe or spawn alongside a healthy service.

The Window menu gained 「显示主窗口 / Show Main Window」 (→ `MenuActions.showMainWindow`) and 「关闭窗口 / Close Window」 (⌘W): the restore path must be reachable from the menu, not just the Dock, and ⌘W stopped being a destructive key. `MainWindow.windowWillClose` logs one line through `ServerManager.log` (non-`private` for this reason) saying the service is still running — otherwise a user who later notices `node` alive concludes the app failed to exit cleanly. `BackgroundResidencyTests` pins the policy flag, the reopen hook under both `hasVisibleWindows` values, `isReleasedWhenClosed` surviving a real `close()`, and both menu entries in both languages.

### State ownership
Three `@MainActor @Observable` singletons, all read directly by views (`@State private var x = X.shared`):

- `ServerManager.shared` — service process, log buffer, state machine.
- `AppState.shared` — UI state shared between menu and views (`showLogs`), plus the long-lived `WebViewController` (must survive SwiftUI view refreshes, so it lives here, not in a view).
- `MenuActions.shared` / `MenuBuilder` — `NSObject` targets for AppKit menu selectors.

### Runtime resolution and packaging (`RuntimeLocator`, `scripts/vendor-runtime.sh`)
The app can start from two different runtimes, and which one it used changes what a failure *means*: the bundled copy failing is our bad release (the user can only wait for us), the machine copy failing is state on their machine (they can fix it themselves). `RuntimeSource` (`.bundled` / `.machine`) carries that distinction into `FailureCause` and the diagnostics report.

- **`RuntimeLocator.plan(...)` is a pure function** over four optional URLs plus `preferMachine`, because every branch here fails as *behaviour*, not as a compile error: ignoring the bundled copy makes the user sit through a 14-minute download for nothing, and ignoring `preferMachine` means they flipped the escape switch and nothing changed. Order: complete bundled pair → machine node + npx-cached dsh → machine node alone (`.needsInstall`) → `.noNode`.
- **A half-bundle counts as no bundle.** node without `bin.js` (or the reverse) can only fail at spawn, while falling back still has a chance of working.
- **`preferMachine` swaps the first two, with two deliberate edges**: with machine node but no dsh it goes to `.needsInstall` rather than quietly reverting to the bundled copy (reverting is precisely what the user turned the switch on to avoid); with no machine node at all it *does* revert to bundled — being able to start beats honouring the preference.
- **Three relative paths (`nodeRelativePath`, `bootJSRelativePath`, `manifestRelativePath`) are the entire contract between `vendor-runtime.sh` and the app.** Change one side only and the bundled runtime is silently never found — it degrades to the npx path with no error anywhere. `RuntimeLocatorTests.layoutMatchesTheVendorScript` pins them against the script text.
- **`swift run` / `swift build` have no `.app` wrapper**, so all three lookups return nil and dev builds transparently use the machine runtime. Bundling never gets in the way of daily development.
- **Vendoring refuses to cross-compile.** `vendor-runtime.sh <arch> <dest>` aborts when `$arch != $(uname -m)`: dsh's tree contains platform-selected `optionalDependencies` (`@img/sharp-darwin-*`, `@koromix/koffi-darwin-*`, `node-addon-require-builtin-darwin-*`, `node-pty` prebuilds), so a tree installed on the wrong host carries the host's `.node` files and dies inside `dlopen` with no readable error. Hence per-arch runners (`macos-15`, `macos-15-intel`), per-arch release dmgs, and `BUNDLE_RUNTIME=1` rejecting a multi-arch `ARCHS`. **universal is not merely unbuilt, it is impossible** — one `node_modules` belongs to exactly one arch.
- **`runtime-pins.json` is the only version source; `latest` is not accepted.** Bundling exists to replace "whatever npx happened to cache" with one version we verified. node tarballs are checked against the pinned SHA256 (from `nodejs.org/dist/v<v>/SHASUMS256.txt`) and a mismatch aborts the build — that check is the single supply-chain gate in the whole pipeline. `manifest.json` (node/dsh/arch) is written next to the runtime so the app can name the bundled version on screen.
- **The escape hatch is `MachineRuntimePreference`** (`UserDefaults` key `preferMachineRuntime`, default off). Most users must never need to know it exists; it is surfaced by the Settings toggle and by `FailureCause.runtimeVersionSkew`'s primary action.

### Signing, hardened runtime, notarization
- Every nested Mach-O is signed **inside-out, individually** (never `--deep`), with `--options runtime` on all of them — hardened runtime is on for *local* builds too, so "works locally, notarized build won't launch" cannot wait until after a release to show up.
- **Entitlements go only where they are needed.** `assets/runtime.entitlements` (allow-jit + allow-unsigned-executable-memory + disable-library-validation) is applied **only to the bundled `node`**: the first two are V8 hard requirements, the third lets user-installed third-party `.node` plugins be `dlopen`ed. The app body gets **no entitlements at all**.
- `--timestamp` only for `Developer ID` identities (it needs the network; the local self-signed identity would just hang).
- `scripts/notarize.sh` runs a **local precheck** first — authority contains `Developer ID Application`, `flags=…runtime`, `Timestamp=` present — because each of those is a one-second local answer to a question Apple would otherwise take minutes to reject. `PRECHECK_ONLY=1` stops there. Then `notarytool submit --wait` → **`stapler staple` onto the `.app`** → `stapler validate` → `spctl --assess` (which answers a different question from `codesign --verify`: whether Gatekeeper will *run* it, not whether the signature is intact). Credentials come from either an App Store Connect API key (`AC_API_KEY_ID` / `AC_API_ISSUER_ID` / `AC_API_KEY_P8`, base64) or Apple-ID + app-specific password (`AC_APPLE_ID` / `AC_PASSWORD` / `AC_TEAM_ID`); the decoded key is written under `umask 077` and removed by a `trap`.
- **Packaging must happen after stapling** — the ticket is attached to the `.app`, so a dmg (or any archive) built earlier does not contain it. `release.yml` orders the steps that way on purpose.

### Service lifecycle (`ServerManager`, the core of the app)
State machine: `starting → running(port) | external(port) | failed(message)`.

- **Port is chosen by the app, never assumed.** `PortStrategy.defaultPort` (3080) is only dsh's composed default (`port: !!js ctx.webStartup.port ?? 3080`), so the app picks the first bindable port from 3080 upward (`PortStrategy.firstAvailable` + `LocalPort.isFree`, scan limit 32) and passes it explicitly with `--port`. Availability is a real `bind()` test, not an HTTP probe — dsh listens tens of seconds before it answers HTTP, so HTTP probing reports a starting server as a free port.
- **Startup attaches to an existing server only after verifying identity.** `DSHProcessIdentity` resolves the port's listeners (`lsof -t`) and checks each command line: it must be a `node` process whose args contain `@deepseek-ai/dsh` or an npm-generated `dsh` bin link. Confirmed dsh + answers HTTP → `.external`. Anything else (a stranger's server, or a dsh that isn't responding yet) → leave it alone and spawn our own on the next free port. Never load an unverified responder into the WebView.
- **Node resolution** (`resolveNode`, the `.machine` half only): newest-mtime nvm version → `/opt/homebrew` → `/usr/local` → `/usr/bin`. `MenuBuilder.resolveNodePath` duplicates this for the language-sync path; keep the two in sync.
- **dsh resolution.** `ServerManager` gathers the four disk facts and hands them to `RuntimeLocator.plan` (above); it holds no policy itself. With a complete bundled runtime the start path waits for **nothing** — no network check, no npx. On the `.machine` path `resolveBootJS` scans `~/.npm/_npx/*/node_modules/@deepseek-ai/dsh/lib/bin.js` and takes the newest; found → spawn immediately (saves 3–5 s) with no network check at all, so once anything is cached the version never moves again; missing → `npx --yes @deepseek-ai/dsh --version`, then re-resolve. That install has a **20 min** timeout because it was measured, not guessed: `0.1.1-rc.2` plus the web profile's dependency tree is 283 MB and took ~14 min on a machine with a warm npm cache and good network. The previous 180 s ceiling did not survive dependency resolution, which means a first launch on a fresh machine *always* failed there — which is also the reason release builds bundle the runtime instead of relying on this path. Caveat that remains by design on the `.machine` path: the dsh version drifts with whatever npx last cached, and `~/.dsh` is shared state that a newer dsh (e.g. the Electron DSH Desktop app's vendored runtime) can migrate into a format an older dsh refuses to boot against — that skew is what `FailureCause.invalidConfig` / `.runtimeVersionSkew` exist to explain.
- **Spawning** runs `node <bootJS> --profile web --port <chosen> --no-open` as a *direct* child with a minimal environment (`HOME`, `PATH` = node bin + system dirs, `TERM`, `LANG`). The argument list is built by the pure `ServerArguments.spawn`, unit-tested because every mistake in it fails as wrong *behaviour* rather than a compile error. Two constraints imposed by dsh: use the `--profile web` form, not the `dsh web` subcommand (`web` is an alias of `--profile web` and rejects parent flags — `web takes none of parent --profile, --patch, …` — and `--patch` is how config overlays get in); and pass `--no-open`, since dsh otherwise opens the system browser itself (`dsh web: opening the default browser; pass --no-open to disable`) and the app window already *is* that page. Direct-child is the whole point: `applicationShouldTerminate` / `applicationWillTerminate` call `stop()` so no orphaned server survives the app.
- **`stop()` kills the whole descendant tree, and the order cannot be reversed.** Terminating only the direct child leaves dsh's plugin-spawned daemons behind (measured: the dsh-doctor supervisor, which ignores SIGTERM outright); once our node exits they reparent to launchd and outlive the app, holding the port and — for an app running from a dmg or an AppTranslocation mount — the mount itself. So `ServerManager.stop()` snapshots the descendants **before** killing anything (`ProcessTree.descendants(of:)`), because after the parent exits every PPID becomes 1 and the tree is unrecoverable; parentage *is* the ownership proof, so no command-line heuristics are needed here (`DSHProcessIdentity`'s guessing exists for the different problem of a stranger on our port). `ProcessTree.terminate` then SIGTERMs all of them, polls `kill(pid, 0)` for `stopGraceSeconds` (1.5 s), and SIGKILLs the survivors — one polite signal was measurably equivalent to doing nothing. The wait is **synchronous** because both termination hooks are: a Task would never get to run. Deepest-first ordering, `root <= 1` refusal, and the SIGKILL escalation are all locked by tests, two of which spawn real processes (a real grandchild, and a `trap '' TERM` process that only SIGKILL can stop).
- **Readiness is detected two ways**, whichever wins: the log line `dsh web: http://127.0.0.1:<port>` (in `ingest`), or a successful HTTP probe (`probePort`, accepts 200–499). The probe path exists so the UI appears in ~2 s instead of waiting 20–30 s for dsh's full init; the dsh frontend renders its own loading state. Hard deadline 90 s.
- **Startup health is a second, layered judgement** (`StartupHealth`), never a replacement for the readiness probe above. Readiness makes the UI appear; health answers "did this start actually work", which is the only sound input to the safe-mode counter. Two necessary conditions: `WebViewController.onPageLoaded` fires (wired through `AppState.init` → `ServerManager.notePageLoaded()`, deliberately a callback so the WebView layer does not depend on the service state machine) **and** the process survives `minimumUptime` from spawn. `Policy.standard` = 20 s uptime / 60 s page-load timeout / 3 consecutive unhealthy starts → safe mode. `evaluate` checks "already healthy?" **before** "has it exited?" on purpose: a process that ran fine for an hour and then quits normally must not count as a failed start, otherwise ordinary daily use would push the counter to the safe-mode threshold (locked by `exitAfterHealthyDoesNotCountAsFailedStart`). `beginHealthObservation` polls every 500 ms because only the clock can produce the "page still not loaded" verdict — the other two facts have callbacks. `settleHealth` clears `observation` when it reaches a verdict, which makes it idempotent: the termination handler and the polling task both fire on an early exit, and without that guard one failure would advance the streak twice. `notePageLoaded` only honours the first load, so a user repeatedly reloading can never postpone the verdict forever. The streak lives in `UserDefaults` (`UnhealthyStreakStore`) because a crash takes in-memory state with it, which would make "3 consecutive failures" unreachable. Adopted `.external` servers are never observed — they are not our process.
- **Failures are typed, not strings.** `ServerState.failed` carries a `FailureCause`, not a message: ten cases, each with a bilingual `title`/`detail` and an ordered `actions: [RecoveryAction]` (`retry` / `viewLogs` / `exportDiagnostics` / `useMachineRuntime` / `open(URL)` / `reveal(path:)`). Invariants locked by tests: every cause is retryable (an environment fix always needs an entry point that isn't "quit and relaunch"), and exactly one action is primary. `primaryAction` is *derived* — `actions.first(where: \.canResolve)`, so **order is priority**: emphasis belongs to the cause, not the action, because the same "retry" that solves most failures is guaranteed to fail again under version skew, and marking both would mark neither. `detail(_:)` runs `SecretMasker.mask` on its way out — that string is rendered on screen and travels in users' screenshots. Actions are *data*; `ContentView.perform(_:)` executes them, which keeps `FailureCause` pure and testable without AppKit. `classify(exitStatus:logTail:runtime:)` is the interesting half: it strips log timestamps, drops the app's own `[dsh-web]` lines (otherwise "❌ 服务意外退出" gets read back as the cause), then looks for a yaml path in an `in <path>` position **plus** a validation verb → a config rejection, falling back to `.abnormalExit(status:message:)` with the last error-marked line. That config branch exists because the real-world failure on the maintainer's machine — dsh refusing to boot on a `.credentials.yaml` whose `version` is a number, written by a newer dsh — otherwise surfaced only as "exit 1". Only the last 40 log lines are considered, so a previous run's error can't be misattributed.
- **The same log line splits into two causes depending on the runtime** (`RuntimeContext`). Bundled runtime → `.runtimeVersionSkew(bundled:path:message:)`, whose primary action is `useMachineRuntime`: our pinned dsh cannot read a `~/.dsh` that a newer dsh has migrated, and telling the user to hand-edit yaml would push our version problem onto them. `.machine` or unknown → `.invalidConfig(path:message:)`, because there the escape switch is either already on or of unknown benefit, and recommending a no-op button is worse than pointing at the file. The skew detail names the bundled version (from `manifest.json`, falling back to 「版本未知」 rather than printing nil) since the user has no other way to see it.
- **Safe mode** (`PluginInventory` + `SafeMode` + `ServerManager.prepareSafeModeIfNeeded()`) is the recovery path for "a plugin makes dsh unbootable". Entered two ways: the persisted `SafeModeStore` flag (`UserDefaults` key `safeModeEnabled`, set by the menu entry) **or** `StartupHealth.shouldEnterSafeMode(streak:)` after 3 consecutive unhealthy starts. Design constraints, all deliberate:
  - **Plugin discovery is a static disk scan, not `dsh --dump-config`** — dumping config requires dsh to boot, and the only reason this inventory exists is the case where it can't. `PluginInventory.scan` reads `~/.dsh/profiles/web/package.json` → `dsh.profile.bundles`, then each bundle's `cordis.patch.yml` (`- insert:` blocks), then the profile's own `cordis.patch.yml` (hand-added `- id:` rows, attributed to the pseudo-bundle `"profile"`). Bundles are scanned first so ids get the more specific attribution. The failure direction is conservative by construction: an exotic YAML form the regex misses leaves a plugin *enabled* — it never mis-disables and never rewrites config.
  - **Only third-party plugins are disabled.** `isFirstParty` is a `@deepseek-ai/` **prefix** check on the bundle name, so `deepseek-ai-lookalike` is third-party (locked by a test). Killing the first-party bundles would leave nothing to recover *into*.
  - **`~/.dsh` is never written.** The disable list is rendered into `~/Library/Application Support/Harness/safe-mode.yml` and applied as the last composition layer via `--patch`. Deleting that file fully restores the original config. A test asserts the path contains `Application Support/Harness` and does *not* contain `/.dsh/`; another parses the rendered YAML with dsh's own bundled `yaml` module (skipped when the profile is absent) so indentation bugs can't ship.
  - **Spawn form is `--profile web --patch <overlay> --port N`**, forced by dsh: `web` is an alias of `--profile web` and rejects parent flags (`web takes none of parent --profile, --patch, …`).
  - **No external adoption while in safe mode** (`start()` skips `adoptExternalService` when `shouldUseSafeMode`): that instance is running with every plugin loaded, so adopting it would show a banner claiming plugins are disabled while nothing is.
  - **`exitSafeMode()` also resets the unhealthy streak** — otherwise the streak is still at threshold and the next launch re-enters safe mode, so the user clicks "exit" and nothing changes.
  - **Overlay write failure degrades to a normal start**, logged. Safe mode is a remedy; its own failure must not also sink a launch that might have succeeded.
  - Surface area: a persistent `SafeModeBanner` in `ContentView` in *all* states (safe mode looks normal, just missing plugins — without the banner users go debug the plugin instead), a `DisabledPluginList` popover, a state-dependent single menu entry (`toggleSafeMode`, title flipped by the 1 s `startGuard` rebuild), and safe-mode status + disable list in the diagnostics report.
- **Restart (`⌘⇧R`)** is intentionally heavy so plugin/config changes take effect: stop own process → poll up to 5 s for the port to be bindable → if still held, `SIGTERM` **only** listeners whose command line verifies as dsh (`terminateVerifiedDSHListeners`; unverified holders are logged and left running) → poll 3 s → relaunch, falling forward to another port if the old one is still taken.
- **Logging**: stdout and stderr share one pipe, drained on the `dsh-web.log` background queue, split on newlines, hopped to the main actor via `ingest`, timestamped, capped at 5000 lines. Entering `.failed` auto-expands the log sidebar (`ContentView.onChange(of: server.state)`).
- **Log persistence** (`LogFileSink` + `LogRotation`): the same already-masked line that goes into the in-memory buffer is also appended to `~/Library/Logs/Harness/harness-<date>[.<segment>].log`. `LogFileSink` confines all mutable state to a private *serial* `DispatchQueue` — deliberately not an actor, because unstructured Tasks on an actor are not FIFO and out-of-order log lines invert cause and effect while debugging. Rotation only ever *adds* segments (never renames), so `chronological` must sort by (stamp, segment): lexicographic order is wrong here (`harness-D.1.log` < `harness-D.log`). Two safety properties are locked by tests: `LogRotation.isOwnedLogFile` gates deletion, so foreign files in the directory are neither counted toward the 16 MB ceiling nor removed; and the segment currently being written is never evicted. Every I/O failure degrades silently to not-logging — a read-only log directory must never take down the service. Directory-ceiling enforcement runs only at rotation moments, because a `contentsOfDirectory` + per-file `stat` on every line would stall writes during dsh's streaming output. `AppDelegate` calls `closeLogFile()` from both termination hooks.
- **Diagnostics export** (`DiagnosticsReport`, 「文件 → 导出诊断信息…」): pure renderer, all environment facts injected by `ServerManager.diagnosticsReport()` so the format is unit-testable. It runs `SecretMasker.mask` over its *final rendered output* even though the log tail is already masked — the report is the artifact that gets pasted into issues, so it gets a last-line-of-defense pass. nil Node/boot paths render as the literal `未解析` rather than blank, because "not resolved" is itself the most common failure diagnosis.
- **Secret masking** (`SecretMasker.mask`) runs in `ServerManager.log(_:)` — the single funnel every line passes through, including the app's own messages — and again on the `.failed` message text, because that string is rendered in the UI. It is an ordered list of `NSRegularExpression` rules, pure and unit-tested: structural matches (Cookie/Authorization headers, URL userinfo, sensitive query params, named JSON/YAML/CLI fields) collapse to `****`; shape-based guesses (`sk-` keys, `Bearer`/`Basic`, alphanumeric runs ≥32) keep a 3-char prefix so two runs of the same value stay comparable. Two deliberate asymmetries, both locked by tests: bare `code`/`key`/`auth` are *not* treated as secrets outside URL query strings (`exit code: 1` and `--port 3080` must survive), and the header rule masks to end of line, which over-masks inline header objects — that is the intended direction, since Cookie values contain their own `;`/`=` separators. The `(?!\*\*\*\*)` assertions make masking idempotent; note the header rule's assertion sits *before* the separator group, because after it the regex backtracks `\s*` to dodge it and eats the space.

### TCC-protected paths: a read that never returns (`Deadline`, `PluginPathAudit`)
On `~/Documents` / `~/Desktop` / `~/Downloads`, an ungranted `open()` does not fail — **it never returns**. `try?` cannot help, and neither can `Task.cancel()`: cancellation is cooperative and a thread parked in the kernel cannot observe it. Nor can a `withTaskGroup` race, because a task group awaits *all* its children and a permanently-suspended child deadlocks the caller. This is not hypothetical — it is the measured failure on the maintainer's machine, where a plugin is symlinked into `~/Documents/dev/…` (linking a dev repo into `node_modules` is ordinary practice) and `sample` shows dsh's **main thread** in `uv_fs_open → open → __open` for 100% of samples, with no output, no error, and no listener ever appearing. `dsh` hangs; the app reports 「无响应」 90 s later; nothing names the cause.

- **`Deadline.run(timeout:qos:)`** is the whole answer: `withCheckedContinuation` + the work on a background queue + a timer on another + a claim-once lock, and the stuck thread is *abandoned*. The abandoned thread eventually finishing and resuming the continuation a second time would **crash the process**, so `DeadlineTests.lateFinishAfterTimeoutDoesNotCrash` actually drives that path rather than asserting about it.
- **The freeze this fixed was ours, not dsh's.** `prepareSafeModeIfNeeded()` scanned the plugin inventory on the main actor; one symlink into `~/Documents` froze the entire UI. It is now `async`, goes through `PluginInventory.scanInBackground` (3 s), and a timeout **starts normally** — writing a 「nothing to disable」 overlay would be a lie that also disables nothing.
- **`PluginPathAudit` is a pre-flight, deliberately not a gate.** `auditPluginPaths()` is fired and not awaited: dsh may well start anyway (the user granted access earlier), and if it doesn't, these three log lines are the only thing that explains the hang — the failure state auto-expands the log sidebar, so the user sees them. Enumeration (`symlinkedIntoProtectedDirectories`) is safe because `readlink` is **not** TCC-gated; only the probe (`unreadable`) needs a deadline. Both are bounded anyway, and **a timeout is reported as "found nothing"**: under-reporting costs a few log lines, while stalling the start path is a real fault.
- **`isInside` appends a path separator** before comparing, so `~/Documents-old` is not counted as inside `~/Documents` — otherwise innocent plugins get named. A broken symlink counts as unreadable on purpose: "can't be opened" is one disposition, whatever the reason.
- **The three `NS*FolderUsageDescription` keys in `build.sh`'s Info.plist exist so the system has something to say.** Child processes inherit the app's privacy grants (we are the responsible process), so the prompt is *ours*; without a usage string there is no prompt to show. Bilingual via `zh-Hans.lproj` / `en.lproj` `InfoPlist.strings` — the only user-visible copy in the app rendered by the system rather than `Strings.swift`.

### WebView (`WebViewController`)
Navigation policy lives in the pure static `shouldStayInWebView(url:isUserInitiated:opensNewWindow:appHost:)` specifically so it is unit-testable — the delegate method only adapts `WKNavigationAction` to it. Rules: new window → external; user-clicked cross-origin → external; same-origin or programmatic (including cross-origin redirects like OAuth callbacks) → stay.

A `linkBridgeScript` user script also patches `window.open` and captures clicks in the capture phase, because the dsh frontend `preventDefault`s external links before WebKit's delegate ever sees them; it posts to the `openExternal` message handler, which validates the scheme is http/https before calling `NSWorkspace.open`.

Two performance mitigations for input lag during agent streaming (WebKit's compositor is less independent than Chromium's): `wantsLayer = true`, and `beginUserActivity()` holding a `ProcessInfo` activity token to prevent App Nap throttling. `⌘⇧O` (open in Chrome/default browser) is the escape hatch when streaming still stutters. **Never set private `WKPreferences` values such as `threadedScrollingEnabled`** — they throw `NSInvalidArgumentException` on macOS 26 and crash at launch.

#### Immersive top: one flat band, and the page never enters it
With `fullSizeContentView` the window's top ~32pt belongs to neither the titlebar nor the page — it is a band that is ours. Two questions had to be answered there, what it shows and how the window gets dragged, and the answers are back to the original ones: it shows `window.backgroundColor`, a transparent AppKit strip restores titlebar behaviour, and the web view stays entirely below the titlebar.

- **The band is one flat colour, deliberately *not* matched to the page** (`WindowChrome.apply`): `window.backgroundColor` = `#151517`, dsh's dark-theme body base (`--dsw-static-neutral-bluish-950`), plus `titlebarSeparatorStyle = .none`, since that hairline would sit between band and page in a third colour. It does not line up seam-perfectly with the page's columns, but it is stable — it does not flicker, does not follow the page, and owes no animation a frame. **0.3.6/0.3.7 did the opposite and it was withdrawn on feel, not on bugs**: an injected probe measured the live page (two `elementFromPoint` samples, walk up to the first opaque `backgroundColor`, 1×1-canvas normalisation so `oklch()`/`color(srgb …)` arrived in Swift as sRGB bytes, `requestAnimationFrame` coalescing, memoised colours) and the band was painted natively as two segments split at the sidebar's right edge. A colour that travels page → native is a frame behind *by construction*, so every moment the band's colour changes — collapsing the sidebar, switching theme, resizing — showed it; the verdict was 「还不如最开始的版本」. All of it is deleted: `topBandProbeScript`, the `topBandColors` message channel, `measureTopBand`, `TopBandColors`, `TopBandView`, `AppState.topBand`, `ContentView.isImmersive`/`paintTopBand`/`syncTopBand`, and `TopBandTests`. **Don't rebuild it**, and don't reach for the page-side alternative either (next bullet).
- **The page is kept *out* of the band, rather than negotiating hit-testing inside it.** `ContentView` deliberately has **no `.ignoresSafeArea(.container, edges: .top)`**, so `NSHostingView`'s safe-area inset places the whole web view below the titlebar and nothing the page renders can be in the band. An earlier design did the opposite — the page reached y=0 and paid for the traffic lights with a `padding-top` on `#root` — and that shipped a real defect: **`padding` displaces only `#root`'s children**, while dsh's two top-right plugin icons (collapse bottom panel / collapse sidebar) are `position: fixed`, i.e. resolved against the *viewport*. They stayed in the band and the drag strip ate their clicks. A whole mechanism for probing "gaps" in the band and restricting the strip to them was built, tested, shipped, and did not work on the user's machine; insetting the web view *deletes* all of it (`topInsetVariable`, `topInsetStyleScript`, `topInsetScript(points:)`, `setTopInset`, `applyTopInset`, `dragRangesMessageName`, `dragRanges(from:)`, `pointermove`/`nearBand`, `TitlebarDragStrip.dragRanges` + its `hitTest` override). **Do not reintroduce page-side layout CSS to reclaim those 32pt** — a flat band is a settled cost, and the click cost is not worth paying twice.
- **Height is measured, never a constant.** `WindowChrome.titlebarHeight(of:)` = `frame.height - contentLayoutRect.height`, which is also exactly the safe-area inset `NSHostingView` applies, so the strip and the layout cannot disagree. It is applied **unconditionally**, through the single exit `ContentView.syncDragStrip()` → `WindowChrome.setDragStripHeight` → `ContentContainerView.stripHeight`: the strip must always exist, or the window is draggable by its border only. Re-measured on `didResize` / `didEnterFullScreen` / `didExitFullScreen`, because full screen collapses the titlebar — the measured height becomes 0 and the container hides the strip, handing the band back to the page. Nothing is gated on whether a status header or the safe-mode banner sits on top any more; that gate (`isImmersive`) existed only to stop the *colours* being painted above our own chrome.
- **`ContentContainerView` + `TitlebarDragStrip` give the band back its titlebar behaviour.** The strip is a transparent `NSView` that calls `performDrag`, returns `acceptsFirstMouse` (a real titlebar drags on the click that also activates the window), and routes double-click through `AppleActionOnDoubleClick` so zoom/minimise/nothing follows the system setting. It claims the **whole** band with no `hitTest` override, which is safe precisely because of the inset above. **It must live in AppKit, not as a SwiftUI `.overlay(alignment: .top)`** — that was the first attempt and it silently did the wrong thing: `ignoresSafeArea` only lets content *draw* into the safe area, while an overlay's layout frame still starts at the safe-area top edge, so the strip landed entirely *below* the traffic lights. The top 32pt stayed WebKit's (still not draggable) and a horizontal band of the page lost its clicks — invisible at compile time and in screenshots, because the strip is transparent. So it is a sibling of the hosting view inside the window's `contentView`, subview order `[content, strip]`: geometry is window coordinates, and z-order is decided (`hitTest` reaches the strip first). Traffic lights are unaffected — they live in the titlebar container, above `contentView` entirely (`hitTest` at (20, top-16) returns `_NSThemeCloseWidget`). `TitlebarDragStripTests` builds a real `NSWindow` with `MainWindow.styleMask` and pins the geometry, that `hitTest` reaches the strip across the whole band, that it does *not* reach it just below the band, that height 0 hides it, and that the height really arrives through `WindowChrome.setDragStripHeight`.

### Single instance (`InstanceLock`, `AppRelaunch`)
`applicationDidFinishLaunching` takes an exclusive `flock` on `~/Library/Application Support/Harness/instance.lock` **before** anything else; failing to get it means another Harness is live, so the app activates that instance (by the pid written in the lock file, else by bundle id) and `exit(0)`s — deliberately bypassing `NSApp.terminate`, since a redundant instance should not touch the shared log directory or `~/.dsh` on its way out. macOS's own "already running" handling only covers re-opening the *same bundle*, so `open -n`, `swift run`, and having both `dist/Harness.app` and `~/Applications/Harness.app` all get through; two live instances mean two dsh servers competing for one `~/.dsh` and interleaving into one log directory.

- `flock`, not a pid file: the kernel drops the lock when the process dies, so a crash can't leave an unopenable app behind. It also makes the lock unit-testable — `flock` locks attach to the *open file description*, so a second `open` + `flock` in the same process is rejected exactly like a second process would be (`fcntl` locks are per-process and would silently succeed, which is both untestable and wrong here).
- **Undecidable means allow.** If the directory can't be created or `open` fails, `acquire()` returns `.acquired`. An extra instance is recoverable; an app that never launches is not.
- The lock file is opened **without** `O_TRUNC` so the incumbent's pid survives to be read by the loser; the winner then `ftruncate`s and writes its own.
- **`AppRelaunch` exists because of this lock.** The old `sh -c "sleep 1 && open <bundle>"` language-switch restart races it: if the outgoing process outlives the sleep, the new instance sees the lock held and kills itself — "switching language made the app disappear". The command now polls `kill -0 <pid>` (0.1 s ticks, 10 s ceiling) and then `open`s unconditionally (`;`, not `&&`, or a timed-out wait would skip the `open`). `command(bundlePath:pid:)` is pure and unit-tested, including double-quote escaping.

### Language switching
Two hand-written menu trees (`buildMenu(language:)`), preference in `UserDefaults` under `appLanguage`, default `.zh`. Switching in Settings also writes `locale.preference` into `~/.dsh/settings.yaml` so the dsh web UI matches — done by shelling out to `node -e` with dsh's own bundled `yaml` module (`~/.dsh/profiles/web/node_modules/yaml/dist/index.js`) and `parseDocument`/`setIn`, which preserves the rest of the file. Applying the change restarts the app through `AppRelaunch.restart()`, because `open` on a still-running instance only activates it.

## Conventions

- Swift 6 strict concurrency: `@MainActor` isolation throughout; `nonisolated(unsafe)` only for the deliberate `MenuBuilder.lastMenu` case.
- One feature per file, ≤800 lines. Prefer immutable values; return copies rather than mutating.
- Everything the app writes goes under `AppDirectories.support` (`~/Library/Application Support/Harness`) or `~/Library/Logs/Harness`. `~/.dsh` is shared with the user and with other dsh versions: read it, never write it (`settings.yaml`'s `locale.preference` is the single sanctioned exception, and it goes through dsh's own yaml parser).
- All user-visible strings are bilingual. New UI copy goes into `Strings.swift` — `Key: CaseIterable` plus an exhaustive `switch` in `localized(_:)`, so a key without both languages doesn't compile, and `StringsTests` walks every key to reject an empty side, an English side containing CJK (the missed translation that actually happens: the English slot copied from the Chinese one), and mismatched `{placeholder}` sets. Interpolation is named `{port}`-style via `Strings.text(_:_:substituting:)`, not `String(format:)`: a mismatched specifier crashes, a missing named placeholder just leaves a conspicuous `{port}` on screen. Three deliberate exclusions: `FailureCause` and `MenuBuilder`'s menu trees are already complete bilingual tables keyed by their own domain types (moving them is churn with no user-visible gain); `ServerManager` log lines stay single-language, because logs get pasted into issues next to dsh's own English output and one language per line stays greppable and comparable across users; and the language names in the Settings picker (`简体中文` / `English`) stay literal, each written in its own language. Repo docs, code comments, and commit bodies are written in Chinese.
- Colors/icons via SF Symbols and AppKit standard controls; the only hardcoded color is the dark window fallback in `WindowChrome`.
- Tests use swift-testing (`@Test`, `#expect`). `ServiceLanguageSyncTests` exercises real `node` + real `yaml`, and returns early when `~/.dsh/profiles/web` is absent (CI runners have no dsh profile) — keep that guard.
- Conventional Commits (`feat:`/`fix:`/`refactor:`/`docs:`/`test:`/`chore:`/`perf:`/`ci:`).
- **In shell scripts, always brace-expand a variable that is followed by a CJK character**: `${IDENTITY}「…」`, never `$IDENTITY「…」`. macOS ships bash 3.2, whose variable-name parsing is not UTF-8 aware — it absorbs the multibyte character into the identifier, and under `set -u` the script aborts with `IDENTITY」: unbound variable`. Since every user-facing string in these scripts is Chinese, this is a standing hazard, and it only fires on the branch that prints the message.

## Release

`git tag` is the single source of truth for versions. Pushing to `main` triggers `auto-release.yml`, which auto-bumps the patch version, pushes the tag, and calls `release.yml` in the same run. Commits whose subject starts with `docs:` or `chore:` are skipped, so use those prefixes to avoid cutting a release. Add a `## [x.y.z]` entry to `CHANGELOG.md` before landing a release-worthy change, otherwise the release notes contain only the commit list.

`release.yml` has three jobs: **prepare** (resolve tag → version, `swift test`, extract the changelog entry) → **build** (matrix `arm64` on `macos-15` / `x86_64` on `macos-15-intel`, `fail-fast: false`, 120 min timeout because vendoring installs dsh's ~250 MB tree and notarization then waits on Apple) → **publish** (`ubuntu-latest`, collect dmgs, concatenate the per-arch `.sha256` files into `SHA256SUMS.txt`, create the release). Assets are `Harness-<version>-macos-apple-silicon.dmg` and `…-intel.dmg`; the notes are prefixed with which one to download, since choosing wrong yields an app that cannot start.

- **Distribution is dmg, not zip** (`scripts/make-dmg.sh`). A zip unpacked in Downloads is still quarantined, and double-clicking the `.app` in place triggers **App Translocation** — macOS executes it from a read-only `/var/folders/…/AppTranslocation/<UUID>/d/` mount whose path changes every launch, which moves the instance-lock path, re-triggers TCC prompts, and made an orphaned dsh grandchild hold the mount open. The dmg carries an `/Applications` symlink so the app is installed before first run. `hdiutil create … -fs HFS+ -format UDZO` deliberately, with **no AppleScript** icon layout or background image: that needs Finder automation permission and fails or hangs on CI runners, while plain UDZO already shows both icons. HFS+ rather than APFS because an APFS dmg will not mount on older systems. `ditto` rather than `cp -R` when staging, to keep the bundled runtime's symlinks, xattrs, and signature structure intact. **The dmg is signed, notarized, and stapled in its own right** — the ticket inside the `.app` does not clear the container's quarantine flag — which is why `notarize.sh` takes a target argument and branches on `MODE` (dmg: submit directly, precheck authority only, `spctl --assess --type open --context context:primary-signature`; app: `ditto`-zip first because notarytool will not take a directory, precheck also demands hardened runtime + timestamp, `spctl --assess --type exec`).

- **Only the *volume* icon is brandable, not the dmg file's.** `make-dmg.sh` stages `.VolumeIcon.icns` at the image root and sets `kHasCustomIcon` (FinderInfo bit `0x0400` at byte offset 8 of the 32-byte `com.apple.FinderInfo` xattr) on the **mounted volume root** — which is why the image is built `UDRW`, attached, tagged, detached, then `hdiutil convert`ed to `UDZO`: the flag lives on the volume root, and the volume root does not exist until the image is mounted. `xattr -wx` rather than `SetFile`, because `SetFile` ships with the Xcode command-line tools while `xattr` is always present. The **dmg file's own** icon cannot be branded in any way that survives distribution: file-level custom icons live in the resource fork / extended attributes, and an HTTP download transfers only the bytes — so a downloaded `.dmg` always shows the generic disk-image icon. Don't spend time on it again.

- **Secrets required for a fully signed + notarized release**: `MACOS_CERT_P12` (base64 of a `.p12` holding a *Developer ID Application* cert + key), `MACOS_CERT_PASSWORD`, `AC_API_KEY_ID`, `AC_API_ISSUER_ID`, `AC_API_KEY_P8` (base64 of the `.p8`).
- **Missing secrets degrade rather than fail.** No `MACOS_CERT_P12` → a `::warning::` and ad-hoc signing (which is what this repo did before signing existed; breaking releases over a newly added step would be the wrong trade). Cert but no API key → sign, skip notarization. `import-signing-cert.sh` prints the identity on stdout and it is deliberately **not** masked: that string, team ID included, is stamped into every signed artifact, and masking it turns the `codesign` log line into `***` exactly when you need to know which cert was used.
- **CI keychain handling** (`import-signing-cert.sh`): a temporary keychain, because the runner's login keychain is locked and unlocking it needs the runner user's password; `set-keychain-settings -lut 21600` so the default 5-minute idle lock can't expire mid-notarization; `set-key-partition-list` — omit it and `codesign` blocks on a GUI authorization prompt, i.e. a hung runner; and `list-keychains -s "$KEYCHAIN" $EXISTING` **appends**, since replacing the list drops the system root chain and signature verification then fails.
- **`follow-upstream.yml`** (daily `17 4 * * *`, off-the-hour to dodge GitHub's cron queue peak; `ubuntu-latest`, since only curl + python3 are needed and macOS minutes cost 10×) runs `check-upstream.sh` and opens a PR when `runtime-pins.json` moves. Bundling traded "version drift" for "we are responsible for following": without this the pins sit at whatever was current on release day, and users get no dsh updates at all. Policy split: **dsh follows npm `latest`**; **node follows only within the pinned major**, because crossing a major changes `NODE_MODULE_VERSION` and every prebuilt `.node` in the tree — that is a port, not an upgrade, and a human decision. The branch name embeds both versions so re-runs don't open a second PR, and the PR body carries a human verification checklist. The pin diff reaches the PR body through a **file**, not a step output interpolated into a shell heredoc: it is git-derived content and must not get a chance to participate in script parsing.
